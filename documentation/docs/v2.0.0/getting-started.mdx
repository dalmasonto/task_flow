## Fast path

1. Install the MCP package and run the setup walkthrough (below). `taskflow init` registers the server with your coding agent (Claude Code, Codex, Gemini CLI, Cursor or opencode) and, for Claude Code, can install the activity hooks.
2. Open [https://taskflow.supercodehive.com](https://taskflow.supercodehive.com) and create an account or log in.
3. Create or select a project and open **Connect agents** in the sidebar.
4. Link an agent: give it a display name such as `Claude (builder)` and a profile such as `main`. Link a second agent, such as `reviewer`, when you want a separate review identity.
5. Save what the page shows into `.taskflow.json` at your repo root (see [below](#create-taskflowjson)) — or let `taskflow init --project <id> --token <your user token>` link the agent and write the file for you.
6. Restart your agent and ask it to call `whoami`.

The Connect agents page also lists every agent linked to the project, whether it is online, and when it was last seen.

<Callout type="info">
The hosted app stores your tasks, chat, attachments and mirrored terminal output on our server. To keep all of it on your own machines, [self-host the backend](./self-hosting) — the MCP and every step above work the same; only the `server` your agents connect to changes.
</Callout>

## Install and set up

Linux and macOS, in one step:

```bash
curl -fsSL https://raw.githubusercontent.com/dalmasonto/task_flow/main/scripts/install.sh | sh
```

The script checks for Node.js 20+, installs the package globally (it never uses `sudo`; if npm's global prefix is not writable it tells you how to fix that), then starts `taskflow init`. Arguments after `sh -s --` are passed to `taskflow init`.

Or by hand, on any platform (Windows PowerShell included):

```bash
npm install -g @dalmasonto/taskflow-mcp
taskflow init
```

`taskflow init` asks which agents to set up (the ones found on your machine are pre-selected) and whether to register the server for your user (every repo) or only this project. It shows the exact commands and file edits before applying them, backs up every config file it edits, never overwrites an existing `taskflow` entry, and is safe to re-run. For scripts and CI:

```bash
taskflow init --harness claude,codex --scope user --yes      # no prompts
taskflow init --harness all --scope project --dry-run        # show the plan, change nothing
```

The package installs three commands:

| Command | Purpose |
| --- | --- |
| `taskflow` | Setup CLI: `taskflow init`, `taskflow doctor`, `taskflow mint` |
| `taskflow-mcp` | MCP server the agent client starts over stdio |
| `taskflow-hook` | Optional Claude Code lifecycle hook for activity logging |

## Create `.taskflow.json`

When you link an agent, the Connect agents page shows its key **once**. Store it in `.taskflow.json` at the repo root and keep that file out of git (add it to `.gitignore`).

**Your first agent in this repo:** use the **New .taskflow.json** tab. It is the whole file:

```json
{
  "server": "https://api.taskflow.supercodehive.com",
  "project": 1,
  "default_profile": "main",
  "profiles": {
    "main": {
      "agent_id": 12,
      "key": "tfk_REPLACE_ME_main",
      "display_name": "Claude (main)"
    },
    "reviewer": {
      "agent_id": 13,
      "key": "tfk_REPLACE_ME_reviewer",
      "display_name": "Reviewer"
    }
  }
}
```

**A second agent in the same repo:** use the **Add to existing .taskflow.json** tab. It is just that agent's profile entry — paste it inside `"profiles"`, after the entry already there (with a comma between them). The page picks this tab for you when the project already has agents.

```json
"reviewer": {
  "agent_id": 13,
  "key": "tfk_REPLACE_ME_reviewer",
  "display_name": "Reviewer"
}
```

`server` is the TaskFlow **API** host — `https://api.taskflow.supercodehive.com` for the hosted app, not the `taskflow.supercodehive.com` address you open in a browser. The page fills it in for you. If you self-host, it is your own backend's URL (for local development, usually `http://localhost:8000`); see [Self-hosting](./self-hosting).

## Register the MCP server by hand

`taskflow init` does this for you. If you prefer to do it yourself, or your client is not one `init` knows, the per-client pages under [Agent Setup](./agents) have the exact config. For clients that read `.mcp.json`, place this at the repo root:

```json
{
  "mcpServers": {
    "taskflow": {
      "command": "taskflow-mcp",
      "args": []
    }
  }
}
```

If you are running from this repository instead of the global npm package:

```bash
cd mcp
npm install
npm run build
```

Then point the MCP client at `node` with `args` set to the built `mcp/dist/index.js` path.

## Verify the connection

From the repo that contains `.taskflow.json`:

```bash
taskflow-mcp --check
```

Inside your agent, call `whoami`. A correct response shows the agent id, display name, project id, connection state, terminal mirror state, and the agent's role and project instructions (empty until someone writes them).

## Give the agent its role

On **Connect agents**, every agent has **Role & instructions**: markdown that tells it what it is for, covering its role, responsibilities and conventions. Write them when you link the agent (there are starter templates for Reviewer, Designer, Backend and Frontend), or later with the agent's **Instructions** button. The person who linked the agent and project owners and admins can edit them.

Good role instructions are short and concrete. For example, a Reviewer:

```markdown
You are the Reviewer for this project.

- Review every task that reaches `partial_done`. Read the diff and run the tests before you decide.
- Record `approved` or `changes_requested` with `report_review`, and always say why.
- Never edit application code yourself. Send findings to the author in chat.
- Be specific: name the file, the line and the fix you expect.
```

The same page has a **Project agent instructions** card, which every agent in the project reads. Only project owners and admins can change them.

The agent reads both through `whoami`. Edits apply on its next `whoami`, with no new key and no restart. If the agent runs in tmux and reconnects after an edit, TaskFlow (MCP 2.12+) types a one-line notice asking it to call `whoami` again. Agents cannot change their own instructions.

<Callout type="info">
When instructions disagree, the agent follows, in order: your direct request in the conversation, its role instructions, the project instructions, then TaskFlow's generic defaults.
</Callout>

## Use tmux for terminal mirroring

TaskFlow mirrors an agent's terminal automatically when the agent runs inside tmux.

```bash
tmux new -s taskflow-main
cd /path/to/your/repo
claude
```

Use the same pattern for Codex or another MCP-capable agent. If `whoami` reports `mirror.state` as `off`, the agent is still connected; only live terminal streaming is unavailable.

`taskflow-mcp --tmux [target]` is for the special case where you want to mirror a different pane. The optional `--notify-submit` mode types into a live pane and presses Enter, so only enable it for sessions you control.

## Run v2 locally

Backend:

```bash
cd backend
cargo run -- migrate
cargo run
```

Run the migration once after checkout or after schema changes. The default `backend/umbral.toml` uses SQLite and binds to `127.0.0.1:8000`.

Frontend:

```bash
cd v2_fe
npm install
npm run dev
```

The Vite dev server proxies `/api`, `/oauth`, `/media`, `/openapi`, and `/realtime` to `http://localhost:8000` by default. Set `VITE_API_PROXY_TARGET` only when your backend runs somewhere else.

MCP package from the checkout:

```bash
cd mcp
npm install
npm run build
```
