## Tool model

TaskFlow v2 exposes 43 MCP tools: 19 for identity, tasks, chat, reviews, sessions and activity, and 24 `design_*` tools for the design surface. Each tool accepts an optional `profile` argument, so one MCP client can act as a different configured profile for a single call.

Use the `reviewer` profile for review work when the repo defines one.

## Identity and discovery

| Tool | Purpose |
| --- | --- |
| `whoami` | Confirm the agent identity, project, connection, and terminal mirror state, and read the agent's role and project instructions |
| `select_profile` | Choose a profile for this terminal after asking the human |
| `list_tasks` | List project tasks, optionally filtered by status or assigned agent |
| `list_channels` | List chat channels this agent can see |
| `list_agents` | List other agents in the project |

### Role and project instructions

`whoami` returns two blocks, each `{ "markdown": string | null, "updated_at": timestamp | null }`:

- `instructions` holds this agent's role instructions, written by a human on **Connect agents**.
- `project_instructions` holds instructions for every agent in the project, written by a project owner or admin.

When either has markdown, the MCP (2.12+) also shows it as readable text below the JSON. Precedence, highest first: the human's direct request, then role instructions, then project instructions, then generic defaults. Edits apply on the next `whoami`. Agents can read these blocks but never write them.

Humans set them in the web app, or over REST. Both endpoints take `{"markdown": string | null}`; the key is required and `null` clears the text.

| Endpoint | Who can call it |
| --- | --- |
| `PUT /api/taskflow/agents/{agent}/instructions` | The human who linked the agent, a project owner or admin, or a superuser |
| `PUT /api/taskflow/projects/{project}/agent-instructions` | A project owner or admin, or a superuser |

`POST /api/taskflow/agents/link` also accepts `instructions_markdown`, but applies it only when the link **creates** the agent. Re-linking an existing agent (same project, display name and profile) ignores it and returns `"instructions_applied": false`; use the agent `PUT` above to change that agent's instructions.

## Task work

| Tool | Purpose |
| --- | --- |
| `create_task` | Create a task, optionally claim it, and optionally attach files |
| `update_task` | Edit task title, description, notes, priority, or add attachments |
| `update_task_status` | Move a task to a valid status |
| `claim_task` | Assign the task to the current agent |
| `report_review` | Record `approved` or `changes_requested` on a task |

Valid statuses are `not_started`, `in_progress`, `paused`, `blocked`, `partial_done`, `done`, and `archived`.

## Messaging

| Tool | Purpose |
| --- | --- |
| `send_message` | Send a markdown message to a channel, with optional file attachments |
| `download_attachment` | Download a message attachment to disk and return the local path |
| `check_messages` | Read unread messages across channels, or read one channel |
| `mark_read` | Advance this agent's read cursor for a channel |

Agents should call `mark_read` after they have read and acted on messages. Otherwise the same messages remain unread.

## Sessions, terminal, and activity

| Tool | Purpose |
| --- | --- |
| `register_session` | Register or reconnect a live agent session |
| `heartbeat` | Update session liveness |
| `capture_terminal` | Stream terminal output into the current session |
| `log_activity` | Record a meaningful activity event, optionally linked to a task |
| `get_activity` | Read recent project activity, optionally filtered by task |

## Design surface

Agents design screens as HTML page fragments built from registered components and a shared token scale. The server composes each page, and humans review it on the design canvas.

Every project renders with shadcn's semantic tokens (built-in neutral defaults fill any the project has not set; project tokens always win). Write `bg-primary text-primary-foreground`, `text-muted-foreground`, `border-border`, `rounded-lg`, with opacity modifiers like `bg-primary/10`. Hex/rgb/hsl or px in brackets (`bg-[#3b82f6]`, `p-[13px]`) and Tailwind's raw palette (`bg-blue-500`, `text-zinc-400`) are rejected on write, and the error names the semantic class to use. `bg-black/50` and `text-white` are fine; custom tokens are reachable as `bg-[var(--your-token)]`, and a project-only colour token such as `colors.brand` also gets `bg-brand`. The served `tokens.css` is a shadcn `globals.css` (`:root`, `:root[data-theme="dark"], .dark`, one `:root[data-theme="<name>"]` per extra theme, `@theme inline`). The `rounded-*` scale derives from a single `--radius`, stored as the `custom.radius` token.

**Named themes.** Token values have the shape `{"light": "...", "<theme>": "..."}` and the document carries `themes: [{"name","label"?}]`. Names match `^[a-z][a-z0-9-]{0,31}$`; `light` always exists, `both` and `all` are reserved, and there are at most 8 themes including light. Non-light themes inherit light. Patch examples: `{"colors":{"primary":{"ocean":"#0af"}}}` sets one theme's value, `null` removes an override, and a `themes` list is the full new order (omitted themes are deleted; renaming onto an existing theme is refused). `design_compare` `themes` must stay within the 24-cell limit. To try a palette, add a theme and compare themes; don't overwrite light.

| Tool | Purpose |
| --- | --- |
| `design_guide` | Short guide for agents: no topic returns an index; topics are `tokens`, `fonts`, `flow`, `primitives`, `pages`. Call before the first design write |
| `design_get_tokens` | Read the token scale: `tokens_json` (source), `tokens_css` (generated shadcn `globals.css`) and `defaults` (names served from the built-in values) and `themes` (the ordered theme list with labels and swatches) |
| `design_write_tokens` | Change the tokens (touches every page): a `patch` of just the tokens you change, or the whole document; `base_version` refuses a stale write; `patch.themes` (the full ordered list besides light) adds, renames (`rename_from`), reorders and deletes themes, and `{"<theme>": value}` edits one theme |
| `design_list_components` | List registered components, their attributes, and where they are used |
| `design_read_component` | Read one component's source and version |
| `design_write_component` | Register or update one custom element |
| `design_delete_component` | Retire a component no page uses |
| `design_read_page` | Read one page's body fragment and version |
| `design_write_page` | Write a page's body fragment |
| `design_delete_page` | Move a page to the trash (restorable by a human) |
| `design_write_asset` | Write an image or other non-page file |
| `design_screenshot` | Render a route at a device viewport (or custom size, full page, light, dark, any declared theme, both, or all, in a device or classic frame, with unsaved token overrides) and return a PNG. `all` returns one image per declared theme in `shots`; a theme that fails carries its own `error` instead of an image, and themes that would overrun the time budget are skipped with an error |
| `design_compare` | Render routes × unsaved design variants × themes (any the project declares) as one labelled grid (split per route when cells would be too small), with contrast checks and, on request, a ready-to-apply token patch per variant |
| `design_read_layout` | Read the page groups, page order, flow links and positions |
| `design_create_group` | Add a named page group |
| `design_update_group` | Rename a group |
| `design_reorder_group` | Move a group to a slot |
| `design_reorder_page` | Move a page within or between groups |
| `design_delete_group` | Remove a group (its pages become ungrouped) |
| `design_link_pages` | Draw a user-flow arrow from one page to another |
| `design_unlink_pages` | Remove a flow arrow |
| `design_arrange` | Apply several layout edits as one write |
| `design_list_comments` | Read human comments pinned to elements of a page |
| `design_resolve_comment` | Mark a comment addressed, with a note |

## Expected lifecycle

```text
whoami
list_tasks
claim_task
update_task_status(status = "in_progress")
log_activity
send_message or check_messages as needed
update_task_status(status = "partial_done")
report_review(profile = "reviewer", decision = "approved" or "changes_requested")
```

The MCP package does not expose v1 timer, local database, or desktop-SSE tools. Those belong to the legacy v1 app under `task_flow/`.
