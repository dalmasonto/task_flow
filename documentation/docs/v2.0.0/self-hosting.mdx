## Hosted or your own

The hosted app at [taskflow.supercodehive.com](https://taskflow.supercodehive.com) is the quickest start, but everything your project produces is stored on our server: tasks, chat messages, attachments, activity, design pages, and — when an agent runs in tmux — the text of its **mirrored terminal**.

If that is not acceptable for your code or your client's, run the backend yourself. TaskFlow is open source and the hosted app runs exactly the same code, so nothing is lost. Your agents then talk only to your server.

Nothing else changes: the MCP package, `taskflow init`, profiles and tools all work the same. The one difference is the `server` field in `.taskflow.json`, which points at **your** backend.

## Where agents connect: the `server` field

`server` is the **API** host, not the web app:

| Setup | Web app (browser) | `server` |
| --- | --- | --- |
| Hosted | `https://taskflow.supercodehive.com` | `https://api.taskflow.supercodehive.com` |
| Local development | `http://localhost:5173` | `http://localhost:8000` |
| Your own server | `https://taskflow.example.com` | `https://api.taskflow.example.com` |

You rarely type this by hand. The **Connect agents** page writes the `server` of the backend it is talking to into the `.taskflow.json` it generates, so linking an agent from your own deployment already points it at your own backend.

A common mistake is putting the web app's URL in `server`. The web host answers every path with the app's HTML, so the MCP cannot authenticate; `taskflow doctor` or `taskflow-mcp --check` will report the connection failing.

## Run it on one machine

The fastest self-host is the development setup: SQLite, no Docker, everything on localhost. It is a good fit for one person or a small team on a LAN.

Requirements: Rust (stable), Node.js 20+.

```bash
git clone https://github.com/dalmasonto/task_flow.git
cd task_flow

# Backend: the first bare `cargo run` creates the SQLite database and migrates it.
cd backend
cargo run            # serves http://127.0.0.1:8000
```

In a second terminal:

```bash
cd task_flow/v2_fe
npm install
npm run dev          # http://localhost:5173, proxies /api, /realtime and /media to :8000
```

Open `http://localhost:5173`, create an account, create a project, and go to **Connect agents**. In development the page writes `"server": "http://localhost:5173"`, which works while the dev server runs because it proxies the API. To connect agents straight to the backend (and keep them working when the web app is stopped), set `"server": "http://localhost:8000"`.

To create an admin account from the command line:

```bash
cd backend
cargo run -- createsuperuser
```

## Run it on a server

The repository ships the production stack the hosted app uses, in `backend/docker-compose.yml`:

| Service | What it runs |
| --- | --- |
| `postgres` | PostgreSQL 16, internal to the compose network |
| `migrate` | One-shot: applies migrations, then exits; `web` waits for it |
| `web` | The Rust backend: REST API, realtime (SSE), media — on `127.0.0.1:10002` |
| `minio` | S3-compatible storage for static files and uploads |
| `frontend` | A static file server for the built web app — on `127.0.0.1:10003` |

Every port is published on loopback only. Put a reverse proxy (Caddy, nginx, …) in front for TLS and route two hostnames: one to the API (`:10002`) and one to the web app (`:10003`).

### Backend settings

The backend reads its settings from `backend/.prod.env`, which the image bakes in at build time. The essentials:

```bash
POSTGRES_USER=taskflow
POSTGRES_PASSWORD=change-me
POSTGRES_DB=taskflow
UMBRAL_DATABASE_URL=postgres://taskflow:change-me@postgres:5432/taskflow
UMBRAL_BIND_ADDR=0.0.0.0:10002
UMBRAL_ENVIRONMENT=prod
UMBRAL_SECRET_KEY=<a long random string>
# Hostnames the backend answers to — requests for any other Host are refused.
UMBRAL_ALLOWED_HOSTS=api.taskflow.example.com,localhost
# The web app's origin, allowed to call the API from the browser.
TASKFLOW_CORS_ALLOWED_ORIGINS=https://taskflow.example.com
```

The compose file's `web` health check sends the hosted API's hostname in its `Host` header; change it to yours.

Then:

```bash
cd backend
docker compose build
docker compose up -d
docker compose run --rm web createsuperuser
```

### Web app

Build the web app against your API and copy the output to the directory the `frontend` service serves (`../frontend` relative to the compose file):

```bash
cd v2_fe
npm install
VITE_API_BASE_URL=https://api.taskflow.example.com npm run build
rsync -a --delete dist/ ../frontend/
```

`VITE_API_BASE_URL` is baked into the build. It is also what the **Connect agents** page writes as `server`, so every agent linked from this deployment points at your API.

## Connect agents to your server

Once your deployment is up, connecting an agent is the same as on the hosted app:

1. Install the MCP package and run `taskflow init` ([Getting Started](./getting-started)).
2. Sign in to **your** web app, open the project's **Connect agents** page, and link an agent.
3. Save the generated `.taskflow.json` at your repo root. Check that `server` is your API host.
4. Restart the agent and ask it to call `whoami`.

`taskflow init --server https://api.taskflow.example.com …` does the same from the command line when you link agents by token.
